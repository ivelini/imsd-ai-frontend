# Корзина и оформление заказа на живом API

> Source: план `.claude/plans/cart-checkout-live.md` (согласован пользователем 2026-11-24) и реализация в `template/src`; контракт бэка — `backend/documentations/api-maps/checkout-frontend.md`, сверен с кодом 2026-11-24
> Collected: 2026-11-24
> Published: 2026-11-24

## Задача

Перевести корзину и оформление заказа с моков на живой API бэка. Мок-корзина жила в памяти
(`cartStore`) с персистом в localStorage и сид-товаром; мок-заказ создавался на клиенте,
читал ту же память и хранился в localStorage `orders`. Мок-справочник оформления — в
`src/data/checkout.ts`. После перехода на API мок-заказ стал бы несовместим с живой корзиной,
поэтому корзина и оформление менялись одной работой.

## Поток оформления (контракт)

1. Корзина → «Оформить заказ». Фронт проверяет форму и непустую корзину, генерирует
   `Idempotency-Key` (crypto.randomUUID), кладёт черновик (данные формы + ключ) в
   `sessionStorage`, вызывает `POST /api/checkout/code` с телефоном. Сервер шлёт SMS и
   возвращает `retry_after` — длительность кулдауна.
2. Страница кода: 4 цифры, кнопка «Подтвердить», повторная отправка с таймером.
3. Подтверждение: `POST /api/checkout` с черновиком, `customer_phone_code` и тем же
   `Idempotency-Key`; гость добавляет `X-Device-Id`. Сервер проверяет код, корзину и остатки,
   создаёт заказ и очищает корзину.
4. Успех 201 → снимок заказа в `sessionStorage`, черновик очищается, переход `/order/[id]`.
5. Неверный код 422 `checkout.phone_code_invalid` → остаться на шаге, очистить цифры.

На шаге кода сервер получает только телефон: состав заказа берётся из текущей корзины при
подтверждении. Позиции в теле подтверждения не передаются; корзину можно менять до подтверждения.

## Эндпоинты

| Метод | Путь | Что |
|---|---|---|
| GET | `/api/reference/checkout` | способы получения/оплаты + `code_ttl_min` |
| GET | `/api/reference/delivery-points?city=…` | точки выдачи города |
| GET | `/api/cart?city=…` | корзина |
| POST | `/api/cart/items` | добавить позицию (`itemable_type` tire/wheel, `itemable_id`, `quantity`, city) |
| PATCH | `/api/cart/items/{item}` | изменить количество (абсолютное значение) |
| DELETE | `/api/cart/items/{item}` | удалить позицию |
| POST | `/api/checkout/code` | выслать SMS-код |
| POST | `/api/checkout` | создать заказ по коду |

Все ответы — `{data: …}`. Заголовки: `X-Device-Id` (гость, 1–64) на корзине и подтверждении,
`Idempotency-Key` на обоих шагах оформления, город слагом в запросе/теле.

## Ответ корзины и адаптер

`{id, city:{id,name}, items:[…], subtotal}`; позиция — `{id, itemable_type, itemable_id, name,
slug, brand:{id,name,slug}|null, quantity, unit_price|null, total|null, available,
delivery:{delivery_min,delivery_max}|null, count_in_stock}`. Цены — рубли числами; `unit_price`
null — цены города нет, позиция недоступна. Картинки и артикула в ответе нет.

Адаптер `toCartView`: `id` строки и `itemable_id` разведены (первый — для PATCH/DELETE, второй —
для кнопок «Купить»), `unit_price` → `price`, картинка — единая заглушка
`/assets/img/wheel-product.png`, бренд — `brand.name`.

## Оформление на фронте

- Справочник оформления читается на сервере (RSC) — `getCheckoutReference()`; варианты и подписи
  не хардкодятся, флаги `requires_pickup_point`/`requires_address` решают, какие поля показать.
- Точки самовывоза — клиентский хук `useDeliveryPoints(city)`; пустой список — самовывоз
  недоступен (остаётся курьер). Одна точка города выбирается автоматически.
- Адрес курьера — структура `{city, street, house, apartment, comment}`; свободную строку бэк
  не принимает. Город в поле подставляется из шапки сайта, правка пользователя перекрывает.
- Согласия — статичная строка макета; на сервер уходят `offer_accepted=true`,
  `privacy_accepted=true` (бэк проверяет только true; текст держит фронт).
- Черновик заказа — `sessionStorage` (`checkout-draft`), снимок заказа — `checkout-order-snapshot`;
  ФИО и телефон не попадают в URL, историю и логи. Прямой заход на `/checkout/code` без
  черновика уводит на `/checkout`.
- Отказы различаются по машинному `code` (`checkout.*`), текст на экран берётся из состояния:
  неверный/истёкший/использованный код, кулдаун 429 с `retry_after`, пустая корзина,
  недоступная позиция/остаток, неверная точка, занятый email, неверный телефон.

## Страницы

- `/checkout` — форма получателя, способы из справочника, точки города, адрес курьера,
  оплата из справочника. Пустой список оплаты — кнопка скрыта.
- `/checkout/code` — OTP, таймер повторной отправки, подтверждение, разбор отказов.
- `/order/[id]` — страница успеха из снимка `sessionStorage`; публичного чтения заказа гостя нет,
  поэтому чужой id или другой браузер — «заказ не найден».
- `/order-status` — статичная подсказка: статус виден на странице заказа после оформления,
  поиск по номеру — с личным кабинетом (мок-поиск удалён).
