# 0004. Город как контекст запроса: резолв фронтом, city в URL

> Source: documentations/adr/0004-city-request-context.md (проектный файл)
> Collected: 2026-08-19
> Published: 2026-08-14

- **Статус:** Accepted
- **Дата:** 2026-08-14
- **Связанные ADR:** 0001, 0002

## Контекст
Цены, наличие и SEO-контент зависят от города. Возник вопрос, кто определяет город для контентных запросов (каталог, SEO-блок): бэк по IP/cookie или фронт через URL. Параллельно решалось, куда класть город в модели запроса — поле фильтра или отдельный параметр.

## Решение
Фронт авторитетен. Город всегда доводится до URL как query-параметр `?city=`: вход по ссылке, выбор в GeoPopup, восстановление из стора при заходе без параметра (`CityHydrator` синхронизирует URL↔store через чистую `citySyncAction`, город персистится в localStorage). Смена города — RSC-навигация (`router.push`): серверные геттеры перевыполняются с новым городом. В сигнатурах геттеров `city` — отдельный аргумент (`getCatalogProducts(filter, city?)`), не поле `FilterState`: это контекст запроса, а не критерий товара.

## Почему (альтернативы)
- Резолв бэком (IP/cookie): бэк владеет бизнес-логикой, но тогда URL лишается города — страдает SEO/индексация (нет канонических URL с городом), а лейблы на странице могут разойтись с фактическим городом бэка. Цена выбора: бэк не видит геолокацию клиента — при пустом параметре применяет свой дефолт.
- `city` внутри `FilterState`: потащил бы город в `useFilterStore`, конфиги URL (`segmentOrder`/`extraQueryFields`) и сравнения фильтров — засорение модели критерия товара контекстом запроса.

## Последствия
URL — единственный источник истины города: ссылки с городом переживают перезагрузку, кэш/CDN дружат с параметром. Смена города = серверный рендер заново (мигание при восстановлении города из стора принято). Бэк получает `city` как query-параметр; без параметра применяет дефолт. Пересмотрим, если понадобится геолокация по IP без URL (клиенты без браузера): контракт допускает резолв бэком при пустом параметре — менять фронт не придётся.
