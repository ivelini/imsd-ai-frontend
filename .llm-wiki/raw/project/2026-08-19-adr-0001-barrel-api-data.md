# 0001. Баррел `shared/api/data.ts` как точка подключения API

> Source: documentations/adr/0001-barrel-api-data.md (проектный файл)
> Collected: 2026-08-19
> Published: 2026-08-07

- **Статус:** Accepted
- **Дата:** 2026-08-07
- **Связанные ADR:** —

## Контекст
`shared/api/data.ts` — God Object: 700 строк, функции 8 доменов (nav, geo, home, catalog, product, cart, checkout, auth, articles) в одном файле, к которому привязаны импорты 32 потребителей. При подключении Laravel API файл стал бы точкой конкуренции в PR: все правки (замена setTimeout на fetch) — в одном месте.

## Решение
Разделить на доменные модули `shared/api/<домен>.ts` (base, nav, geo, home, service-pages, catalog, product, cart, checkout, auth, articles, seo). `data.ts` остаётся баррелом (`export *`) — контракт импортов потребителей не меняется. Подключение API = замена моков на fetch внутри модулей, баррел и потребители не трогаются.

## Почему (альтернативы)
Рассматривали перевод 32 потребителей на прямые доменные импорты (`@/shared/api/cart`): честная зависимость от домена, но 32 файла правок сразу, а при API всё равно одна точка замены внутри модулей — баррел дешевле и стабильнее. Оставить как было — экономия сейчас, гарантированный конфликтный PR при API. Цена выбора: прослойка барреля между потребителями и доменами.

## Последствия
Контракт импортов заморожен на время мок-фазы (потребители не знают о модулях). `export *` слегка расширил публичную поверхность (delay стал экспортируемым — безвредно). Пересмотрим: при подключении API, если потребителям понадобятся разные доменные модули, баррел можно убрать постепенно.
