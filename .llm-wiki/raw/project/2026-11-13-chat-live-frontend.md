## Интеграция: публичный чат (ИИ-ассистент)

Проверено 13.11.2026 по ../backend/documentations/api-maps/public-chat.md,
public-chat-frontend.md и Scramble-экспорту public-api.json.

Запросы идут через apiBase(): сервер — BACKEND_URL, браузер — /api через rewrites()
в next.config.ts.

### Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| POST | /api/chat | Вопрос {message} 1–2000 символов → 202 {session_token, message_id, status}; без X-Session-Token создаёт диалог |
| GET | /api/chat/messages | Реплики {data: [{id, role, content, created_at}]}; заголовок X-Session-Token обязателен; без after_id — последние до 200 реплик |

Токен — uuid, только заголовком X-Session-Token. Роли наружу — user и assistant; служебные
system не отдаются. created_at — ISO с таймзоной (бывает null).

### Ошибки (различение по статусу и code, не по тексту)

| Статус | Что делает фронт |
|---|---|
| 400 ai.off_topic | Текст бэка плашкой в ленте; реплика не записана, введённый текст остаётся |
| 404 | Токен протух: токен стирается, остаётся приветствие; следующий POST создаёт новый диалог |
| 422 | Технические ключи validation.* на экран не пускаются — общий текст |
| 429 | Текст бэка (лимит/бюджет), поллинг останавливается |
| 5xx / сеть | «Сервис временно недоступен» + «Повторить» (возобновляет опрос, POST не повторяется) |

### Фронт

- src/shared/api/chat.ts — DTO и запросы; src/shared/api/http.ts — readJson, ApiError,
  toErrorResponse (общие с booking).
- src/features/chat/lib/ — чистые правила: errors.ts (статус+code → состояние), time.ts
  (ISO → «ЧЧ:ММ»), polling.ts (опрос до 60 с, продление повтором), session.ts (токен в
  localStorage chat_session_token).
- src/features/chat/api/ — useChatMessages (React Query, поллинг полным списком раз в 1,5 с,
  пока последняя реплика — вопрос пользователя и не истекло 60 с), useSendChatMessage.
- src/features/chat/components/ — ChatWidget (панель: до 639 px круглая кнопка, с 640 px
  плашка) и ChatWindow (лента, приветствие, ошибки, ввод до 5 строк, ресайз за левый
  верхний угол). Смонтирован в src/app/layout.tsx на всех страницах.
- Стили — блок .chat-* в конце src/app/style.css (13.11.2026), перенос макета .template/chat/.

### Ограничения контракта

- Город не передаётся: чат отвечает по городу магазина по умолчанию.
- Стрима нет (SSE/WebSocket) — только поллинг.
- Лимиты: 20 сообщений в сутки на диалог, 200 на канал, 10 POST/мин и 60 GET/мин с IP;
  диалог хранится 30 дней.
- Ответ с внутренней лексикой бэк заменяет на «Не могу ответить на этот вопрос» — показываем
  как есть.

## ТЗ: витрина публичного чата не должна отдавать пустые реплики ассистента

- Статус: не выполнено; дата 2026-11-13; адресат — бэкенд imsd-backend (Laravel).

### Проблема

На шагах вызова инструментов агент сохраняет реплику assistant с пустым content:
AbstractAgentLoop::addAssistantMessage пишет $response->text, а на тул-колле текст пустой.
PublicChatMessagesReader отдаёт все реплики ролей user/assistant и не фильтрует пустые.

Следствия на фронте:
1. В ленте появляется пустой пузырь ассистента.
2. Поллинг считает диалог отвеченным, как только последняя реплика — assistant, и
   останавливается. Настоящий ответ приходит следующей репликой через 1–2 с и до
   перезагрузки страницы не показывается.

Доказательство (dev, 13.11.2026, вопрос «какие зимние шины подойдут на 205/55 R16»):

id 70469 user      "Подскажите, какие зимние шины подойдут на 205/55 R16?"
id 70470 assistant ""                    — пустая реплика, шаг инструментов
id 70471 assistant "Зимние шины 205/55 R16 в наличии (цены ...)"

### Что нужно от бэка

Витрина публичного диалога отдаёт только реплики с непустым content:
- PublicChatMessagesReader::after() — исключить assistant с пустым content (where content != ''
  либо фильтр после выборки с сохранением семантики лимита PAGE = 200);
- шаги инструментов в публичной витрине — служебные, как system: наружу не идут.

Допустимая альтернатива — не создавать пустую assistant-реплику в addAssistantMessage,
если $response->text === '' и есть вызовы инструментов.

### Критерии приёмки

- GET /api/chat/messages не содержит реплик assistant с пустым content на любом сценарии
  с инструментами.
- После пустой реплики витрина возвращает только непустой ответ; поллинг фронта дожидается
  его без перезагрузки.
- Покрыто тестом бэка: диалог с шагом инструмента — в ответе нет пустого assistant.

### Фронт

Фронт не меняется (решение пользователя 13.11.2026): пустые реплики не фильтруются.
До выполнения ТЗ виджет временно показывает пустой пузырь и может не дождаться ответа
до перезагрузки.

## Решения плана chat-live (13.11.2026)

- Лаунчер: мобильный — круглая кнопка, десктоп — плашка с подписью (ответ пользователя).
- Пустой диалог: статичное приветствие ассистента, исчезает с первой репликой.
- Таймаут 60 с: кнопка «Повторить» возобновляет GET-опрос ещё на 60 с, POST не повторяется.
- Поллинг полным списком (без after_id): контракт отдаёт до 200 реплик, лимит 20 сообщений
  в сутки — накопление не нужно.
- Правило двух: readJson, ApiError, toErrorResponse вынесены в shared/api/http.ts; booking
  переведён на них (BookingApiError удалён, контракт поведения прежний).
- Прогоны: красный — 3 файла «Cannot find package»; зелёный — 31 файл / 172 теста, tsc чисто,
  lint 0 ошибок. Живой прогон: POST 202, GET 200, ответ получен.
