# 0009. Статьи и системные страницы — одна сущность Article, URL не сливаются

- **Статус:** Accepted
- **Дата:** 2026-11-05
- **Связанные ADR:** 0001 (баррел `shared/api/data.ts`), 0007 (адреса карточек зеркалят API)

## Контекст
Бэк ввёл статьи: блог и системные страницы — одна сущность `Article` с `type: blog|system`;
отдельного API сервисных страниц больше нет. На фронте исторически два семейства адресов:
`/articles/{slug}` — блог и `/service-page/{slug}` — системные страницы. Ссылки шапки и
футера — это ссылки на системные статьи, но часть пунктов фиксирована продуктом
(«Шиномонтаж» и «Статьи» в шапке, «Каталог» и «Статьи» в футере).

## Решение
- Оба URL сохраняются. `/service-page/{slug}` — системная статья через тот же
  `GET /api/articles/{slug}`, что и блог.
- Пункты меню приходят из `GET /api/reference/article-menu`; фиксированные пункты живут
  в коде фронта и стоят вокруг меню.
- Меню недоступно или не ответило за 3 с — layout не падает, остаются только фиксированные
  ссылки.
- Список блога — серверный: категория и страница в URL, фильтр по корневым категориям,
  пагинация ссылками.

## Почему (альтернативы)
Слить оба семейства в `/articles` — ломает существующие адреса и требует редиректов,
которых на фронте нет; отклонено в плане. Отдавать фиксированные пункты из меню — их
может сломать контент-менеджер, а продуктовая навигация должна быть стабильной. Клиентская
фильтрация и React Query — лишний слой: бэк уже отдаёт готовые данные, пагинацию и
подкатегории. Цена: два URL для одной сущности; тип статьи не виден в адресе.

## Последствия
Проще: один API-слой и одна модель для блога и системных страниц; меню правится в админке
без деплоя. Сложнее: системная статья, открытая по `/articles/{slug}`, рендерится как
бложья — отдельного 404 по типу нет. Пересмотрим, если SEO потребует единого пространства
URL или появятся отдельные шаблоны системных страниц.
