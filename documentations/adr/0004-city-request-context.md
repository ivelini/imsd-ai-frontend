# 0004. Город как контекст запроса: city в URL, резолв бэком

- **Статус:** Accepted
- **Дата:** 2026-08-14 (обновлено 2026-08-21: резолв города переехал с фронта на бэк)
- **Связанные ADR:** 0001, 0002

## Контекст
Цены, наличие и SEO-контент зависят от города. Возник вопрос, кто определяет город для контентных запросов (каталог, SEO-блок): бэк по IP/cookie или фронт через URL. Параллельно решалось, куда класть город в модели запроса — поле фильтра или отдельный параметр.

## Решение
Фронт авторитетен. Город всегда доводится до URL как query-параметр `?city=<слаг>`: вход по ссылке, выбор в GeoPopup, восстановление из стора при заходе без параметра (`CityHydrator` синхронизирует URL↔store через чистую `citySyncAction`, город персистится в localStorage). Смена города — RSC-навигация (`router.push`): серверные геттеры перевыполняются с новым городом. В сигнатурах геттеров `city` — отдельный аргумент (`getCatalogProducts(filter, city?)`), не поле `FilterState`: это контекст запроса, а не критерий товара.

**Резолв слага — на бэке (с 21.08.2026):** листинг каталога принимает `city=<слаг>` (и `city_id` для совместимости) и сам находит город с приоритетом `city_id` → слаг → дефолт из `config/shop.php`. Несуществующий слаг не даёт 422 — фолбэк на дефолтный город (старые/битые ссылки не ломают страницу). Резолв id до кеша (`value('id')`), модель загружается только при промахе кеша — кеш-hit без лишних запросов. Фронт не резолвит id и не делает предварительный запрос гео ради листинга (один RTT на страницу); гео-справочник нужен шапке/попапу и `cityLabel`.

## Почему (альтернативы)
- Резолв бэком по IP/cookie: бэк владеет бизнес-логикой, но тогда URL лишается города — страдает SEO/индексация (нет канонических URL с городом), а лейблы на странице могут разойтись с фактическим городом бэка. Выбор «слаг в URL + резолв бэком» сохраняет канонические URL и убирает с фронта словарь слаг→id (фронт не строит словари — правило api-contract).
- Резолв id фронтом (словарь слаг→id из гео): требовал двуфазных запросов (гео → листинг) на каждой странице и дублировал справочник городов на фронте.
- `city` внутри `FilterState`: потащил бы город в `useFilterStore`, конфиги URL (`segmentOrder`/`extraQueryFields`) и сравнения фильтров — засорение модели критерия товара контекстом запроса.

## Последствия
URL — единственный источник истины города: ссылки с городом переживают перезагрузку, кэш/CDN дружат с параметром. Смена города = серверный рендер заново (мигание при восстановлении города из стора принято). Слаги городов в БД обязательны для URL-совместимости (nullable — фолбэк на дефолт; сверить/заполнить при заведении городов). Пересмотрим, если понадобится геолокация по IP без URL (клиенты без браузера): контракт допускает резолв бэком при пустом параметре — менять фронт не придётся.
