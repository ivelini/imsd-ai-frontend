# Coder mode — Next.js (template, aalyans.ru)

Цель — выполнить план шаг за шагом, не выходя за бюджет, и писать код по правилам проекта.
Процесс планирования — `/planning-mode-fe`; здесь только реализация.

## Профиль проекта

- Слои: `src/app/` — роутинг и композиция; `src/features/<домен>/` — домен (`components`,
  `api`, `types`); `src/shared/` — ядро (`api`, `ui`, `layout`, `lib`, `types`);
  `src/data/` — моки; `src/stores/` — Zustand только UI; `.template/` — HTML-макет.
- Правила: `CLAUDE.md`; `.claude/rules/frontend-architecture.md`, `ui-porting.md`,
  `api-contract.md`, `base.md`, `git.md`, `wiki-sync.md`; глобальные
  `~/.claude/rules/plans.md`, `simplicity.md`, `coding-style.md` — принципы без Laravel-механики.
- Команды: `npm test`, `npm run lint`, `npx tsc --noEmit`. Build и dev-сервер не запускать
  при работающем dev-контейнере (общий `.next`); dev — `make up`, порт 30034.
- Next 16: перед кодом на новых API читать `node_modules/next/dist/docs/` (правило `AGENTS.md`).

## Шаг 0. Гейт готовности

1. Найди план в `.claude/plans/`. Планов несколько — спроси, какой; не угадывай.
2. В плане есть цель, задачи с контрактом шага, бюджет сложности, тест-лист, «не делаем»,
   STOP-условие и строка `**Согласовано:**`. Строки нет — спроси пользователя, подтверди
   и допиши её.
3. Чего-то нет — вернись в `/planning-mode-fe`; код не писать.

## Шаг 1. Красный

1. Создать только тесты по тест-листу в `tests/unit/*.test.ts`; файлы `src/` не трогать.
2. Прогнать `npm test` и показать падение: в TypeScript это `Failed to resolve import "@/..."`
   / `Cannot find module` или проваленная проверка — функции ещё нет.
3. Пока красный прогон не показан, файлы реализации не создавать. Исключение — страж-тесты
   (контракты-отрицания), они законно зелёные.

## Шаг 2. Зелёный

Перед правкой существующего символа открой его через `codegraph_explore`: один вызов даёт
исходник, вызывающих и радиус правки. Инструмента нет — `Read`/`Grep`. Next-специфичный код
сверяй с `node_modules/next/dist/docs/`. Правка вслепую по памяти запрещена.

Реализуй ровно контракты шагов плана: файл::функция, вход → выход. Новые сущности — только
из бюджета плана.

Правила по слоям:

- `src/app/` — роутинг и композиция; по умолчанию Server Component; `"use client"` только
  под интерактив, браузерные API или мутации. Бизнес-логики в странице нет.
- `src/features/<домен>/` — компоненты, хуки, api, types домена. Домены не импортируют
  компоненты друг друга; разрешены типы, `shared/types`, `shared/ui`, `shared/lib`.
- `src/shared/` — только общее для двух и более потребителей или годное вне домена. Помощник
  одного домена — рядом с потребителем, не в `shared/`.
- `src/data/` — моки; компоненты не импортируют `@/data/*` напрямую.
- `src/stores/` — Zustand только UI; корзина и сессия — React Query + localStorage.

Данные и состояние:

- Запросы — через `src/shared/api/` и `apiBase()`; DTO бэка snake_case → тип фронта; адаптер —
  чистая функция. `fetch` в компоненте — нет.
- Сбор данных на клиенте через `useEffect` запрещён; клиентские данные — React Query.
- Фильтры и пагинация — в URL, не в состоянии компонента.
- Клиентская фильтрация и бизнес-логика запрещены — решает бэк.
- Данные для отображения — готовые `{label, value}`/строки от бэка; фронт не строит словари.
- API-контракт — по Scramble-экспорту, не по мокам.

Вёрстка и стиль:

- Разметка 1-в-1 из `.template/`; семантические теги без смены классов; `<img>`, не
  `next/image` (правило ui-porting, ESLint это учитывает).
- BEM-классы, без Tailwind и CSS-in-JS; стили — `src/app/style.css`, новые блоки — в конце
  с пометкой даты. Стили непортированного домена остаются в `.template`.
- TypeScript strict, `@/*`; типы DTO не выдумывать; локальные типы — в домене, общие —
  в `shared/types`.
- Принципы `coding-style.md` без Laravel-механики: чистые функции под unit-тесты, guard clauses
  вместо `else`, fail fast, правило двух, никаких абстракций «на будущее».

## Шаг 3. Рефакторинг

После зелёного: стиль, дубли, лишние слои, «на будущее». Поведение не меняется. Новые паттерны
и сущности не вводятся; нужен паттерн — STOP и правка плана. Если доступен `/simplify` —
прогнать по изменённым файлам.

## Шаг 4. Проверки

- `npm test`, `npm run lint`, `npx tsc --noEmit`.
- `npm run build` / `npm run dev` не запускать при работающем dev-контейнере (общий `.next`
  повреждается). Визуальная проверка — в запущенном приложении (`make up`, порт 30034).
- Красный и зелёный прогоны записать в «Прогоны» плана.
- Если в проекте есть `graphify-out/graph.json` — после правок `graphify update .`.
- Документация по глобальному правилу: env/крон/деплой → `documentations/operations.md`,
  интеграции → `documentations/integrations/`, API → `documentations/api-maps/`, решение →
  ADR (спросить пользователя).
- Wiki-sync: если изменение затрагивает бизнес-логику или функционал — перед завершением
  предложить обновить wiki (`.claude/rules/wiki-sync.md`); косметика — можно закрывать.

## Шаг 5. Отчёт

План против факта: шаги, отклонения, прогоны, что осталось. Без просьбы не коммитить; после
коммита напомнить, что пуш и выкладка — за пользователем. В сообщении коммита указать
`model: <имя>`.

## STOP-условия — жёстко

- Новая сущность вне бюджета плана; правка за пределами шага или плана.
- Новая зависимость (React Testing Library, библиотека), новый маршрут, новый API-контракт
  или мок, новая настройка/env/config.
- Кросс-доменный импорт компонентов.
- Тест не покрывает найденное поведение — дополнить тест-лист вместе с пользователем.
- Нужен паттерн — вызови `/patterns-mode`, остановись и правь план (`simplicity.md`).
- Поведение расходится с планом или архитектурой — обновить документ/ADR или отступить;
  решает пользователь.
- Неясно, как работает API Next 16 — сначала документация в `node_modules/next/dist/docs/`,
  потом код.
- Дифф больше названного в плане числа файлов/строк.

Во всех случаях — стоп и вопрос, а не «допишу по ходу».
