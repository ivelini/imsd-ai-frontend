# Review — Next.js (template, aalyans.ru)

Третий шаг цикла: `/planning-mode-fe` (план) → `/coder-mode-fe` (реализация) → `/review-fe`
(сверка и рефакторинг). Поведение не меняется, новых сущностей не появляется.

**Как выполнять.** Проходи шаги строго по порядку и не пропускай ни один. Каждый шаг
заканчивается доказательством в чате — выводом команды, отчётом агента, таблицей нарушений.
Шаг без доказательства считается невыполненным.

**Обязательность — жёстко.** Пропущенный шаг, сокращённая проверка и отчёт без таблицы —
незаконченное ревью, а не «сделал по-быстрому». «Находок нет» — тоже результат, но его
нужно показать. Ревью не завершается, пока не пройдены все шаги и самопроверка.

## Шаг 0. Гейт — выполни

1. Проверь, что есть незакоммиченные изменения кода: `src/`, `tests/`, `.template/`, `package.json`,
   `next.config.ts`, `eslint.config.mjs`, `tsconfig.json`, `vitest.config.ts`, `server.mjs`,
   `Makefile`, `docker/`. md, доки, `.claude/`, wiki и планы кодом не считаются.
2. Ревью этого же набора уже выполнено в этом ходе — сообщи «Ревью выполнено» и выйди.
3. Найди план в `.claude/plans/`: набор ему соответствует — план читается как контракт. Планов
   несколько — спроси, какой; набор покрывает несколько (последовательные части одной фичи) —
   назови все и проверяй против каждого.
4. Источники правил: `CLAUDE.md`, `.claude/rules/*.md`; глобальные `~/.claude/rules/plans.md`,
   `simplicity.md`, `coding-style.md` — из последнего брать принципы, Laravel-механику
   (`Action`, `Preconditions`, `DTO`, `Resource`, миграции) не переносить.
5. Меняется код на новых API Next 16 — сверять с `node_modules/next/dist/docs/` (правило
   `AGENTS.md`), а не по памяти.

**Доказательство:** назови план(ы) и состав набора.

## Шаг 1. Контекст — выполни

1. Выполни `git status --porcelain`, `git diff`, посмотри untracked — читай полностью.
2. Прочитай источники: план(ы), `CLAUDE.md`, `.claude/rules/frontend-architecture.md`,
   `ui-porting.md`, `api-contract.md`, `base.md`, `git.md`, `wiki-sync.md`; ADR
   (`documentations/adr/`) и wiki-индекс — если вопрос об архитектуре или решении; Scramble
   `../backend/documentations/scramble/public-api.json` — если меняется API; `documentations/`
   — если меняются интеграции или эксплуатация.
3. Сформулируй суть набора — 3–5 строк.

**Доказательство:** суть набора в чате и список файлов.

## Шаг 2. Агент — выполни

1. Проверь `.claude/agents/architecture-reviewer.md`.
2. Файла нет — создай по каркасу `~/.claude/skills/review/references/architecture-reviewer.md`,
   заполнив по документации проекта: «Профиль проекта» в `CLAUDE.md`, правила и ADR проекта,
   команды проверки. Чек-лист другого проекта не переноси.
3. Агент доступен — запусти Agent tool, `subagent_type: architecture-reviewer`: передай суть,
   список файлов, путь(и) к плану и ссылки на источники; дождись отчёта, не пересказывай заранее.
4. Субагентов в клиенте нет или агент не зарегистрирован — проверь сам по чек-листу Шага 3.

**Доказательство:** отчёт агента в чате (или ручной отчёт по чек-листу, если агента нет).

## Шаг 3. Что проверяется — выполни в этом порядке

1. **План vs факт:** сущности только из бюджета, контракты шагов соблюдены, тест-лист покрыт,
   отклонения названы.
2. **Слои и границы:** `src/app/` — роутинг и композиция, `src/features/<домен>/` — домен,
   `src/shared/` — ядро, `src/data/` — моки, `src/stores/` — только UI. Домены не импортируют
   компоненты друг друга; `shared/` — только для двух и более потребителей.
3. **Server/client:** серверный по умолчанию; `"use client"` только под интерактив, браузерные
   API или мутации; бизнес-логики в компонентах роутинга нет.
4. **Данные:** только через `src/shared/api/`; компоненты не импортируют `@/data/*`; DTO бэка →
   адаптер → тип фронта; нет `fetch` в компонентах; API по Scramble, не по мокам.
5. **Состояние:** фильтры и пагинация — URL; клиентские данные — React Query; Zustand — только
   UI; нет `useEffect` для запросов и клиентской фильтрации.
6. **API-контракт:** `{label, value}` и строки для показа — от бэка; `value` = сегмент URL;
   фронт не строит словари и маппинги.
7. **Вёрстка:** разметка 1-в-1 из `.template/`; семантические теги; BEM; без Tailwind; `<img>`
   по правилу ui-porting; стили — `src/app/style.css`, новые блоки в конце с пометкой даты.
8. **Простота:** правило двух; нет абстракций «на будущее», интерфейсов с одной реализацией,
   слоёв-делегатов, мёртвого кода, дублей правил; нет Laravel-сущностей (`Action`,
   `Preconditions`, `DTO`, `Resource`) — здесь их место занимают компоненты, хуки и адаптеры.
   Нужен паттерн — STOP и `/patterns-mode` (в review паттерны не вводятся).
9. **Тесты:** Vitest, `tests/unit/*.test.ts`, чистая функция, имя `test_...`, покрытие
   тест-листа. Компонентных тестов нет — React Testing Library не установлена.
10. **Типы и стиль:** TypeScript strict, `@/*`, DTO не выдуманы, комментарии «почему», а не «что».
11. **Профиль работы с сетью:** интервалы поллинга и повторных запросов, payload и кеш —
    не перечитывать тяжёлые данные без нужды; на горячем пути названы ожидаемые запросы,
    строки и байты; долгие запросы не блокируют старт.
12. **Документация и решения:** env/крон/деплой → `documentations/operations.md`; новая или
    изменённая интеграция → `documentations/integrations/`; API-контракт → `api-maps/`;
    архитектурное решение — предложить ADR; изменения функционала — строка «нужно обновить
    wiki» (`wiki-sync.md`).

**Доказательство:** таблица проверок в чате (пункт → результат).

## Шаг 4. Исправления — выполни только рефакторинг

1. Меняй только нарушения; поведение не меняй; новых сущностей не добавляй.
2. Сначала убедись, что тесты зелёные; после правок прогони снова.
3. Исправление упирается в STOP-условие — остановись по разделу «STOP-условия — жёстко»
   и задай вопрос. Нарушение вне набора — зафиксируй в таблице, не чини.
4. План расходится с кодом — остановись и правь план вместе с пользователем.

**Доказательство:** список исправлений в чате (файл:строка → что сделано) или «нарушений нет».

## Шаг 5. Прогоны и отчёт — выполни

1. Запусти `npm test`, `npm run lint`, `npx tsc --noEmit`; вывод покажи в чате. Build
   и dev-сервер не запускать при живом dev-контейнере (общий `.next`).
2. Если в проекте есть `graphify-out/graph.json` — после правок `graphify update .`.
3. Запиши прогоны в раздел «Прогоны» плана, если план есть.
4. Дай отчёт: таблица нарушений (файл:строка, правило, исправлено/нет), план vs факт, прогоны
   до/после, что осталось и почему.
5. Не коммить; пуш и выкладка — за пользователем.

**Доказательство:** вывод команд в чате, заполненные «Прогоны», таблица нарушений.

## STOP-условия — жёстко

- Новая сущность, зависимость, настройка/env/config, маршрут, API-контракт или миграция.
- Изменение поведения.
- Правка файлов, которых набор не касается, — зафиксируй нарушение в таблице, не чини.
- План расходится с кодом.
- **Находка требует паттерна:** вызови `/patterns-mode`, остановись и правь план вместе
  с пользователем. Паттерн в review не вводится — review лечит нарушения, а не проектирует
  (`simplicity.md`: паттерн без названной второй копии в код не идёт).
- Тест не покрывает найденное поведение — дополни тест-лист вместе с пользователем.
- Неясно, как работает API Next 16, — сначала документация в `node_modules/next/dist/docs/`.

Во всех случаях — стоп и вопрос, а не «допишу по ходу». Пропуск STOP-условия — незаконченное
ревью.

## Самопроверка перед завершением — выполни

Пройди и назови по пункту:

1. Агент запущен (или ручной чек-лист пройден) и его отчёт показан?
2. Все двенадцать пунктов проверок пройдены в порядке из Шага 3?
3. Исправления — только рефакторинг без изменения поведения?
4. Ни одно STOP-условие не обойдено молча?
5. Команды проверок прогнаны, вывод показан, «Прогоны» заполнены?
6. Таблица нарушений и отчёт «план vs факт» даны?

Любое «нет» — шаг не закончен: вернись и выполни его, потом завершай.
